## Контекст

Проект меняет формат: вместо записи к психологам это площадка онлайн-уроков от специалистов в разных областях. Главная новая возможность - ИИ-обработка записи урока:

```
запись урока → [1. транскрибация] → реплики с таймкодами
                                          ↓
                          [2. материалы через LLM: конспект, вопросы и ответы]
```

Этап 1 (транскрибация) сделан, этап 2 ещё не начат.

Новый код встроен в слои, которые уже были в проекте:

```
api (FastAPI)  →  services (бизнес-логика)  →  crud (DAO)  →  models (SQLAlchemy, PostgreSQL)
```

- **api** только принимает запрос, достаёт пользователя из токена и вызывает сервис.
- **services** решает, можно ли это делать и что именно отдать. Все проверки доступа живут здесь.
- **crud** (DAO) - только запросы к базе, без правил.
- DAO не фиксируют транзакцию сами: это делается один раз в конце запроса. Один запрос - одна транзакция, и при ошибке на полпути в базе не остаётся половины изменений.

**Ограничения, которые повлияли почти на все решения:** проект учебный, бюджета и платных ключей нет, сервер - обычный компьютер без видеокарты.

## 1. Модель данных: урок, транскрипт, участники

**Вопрос.** К чему привязывать запись и её расшифровку, где хранить результат и как хранить, кому он доступен? В проекте уже есть «занятие» (`appointments`): слот в расписании, специалист и клиент.

**Варианты.**

Привязка записи:

1. Сначала перестроить весь домен под уроки, потом делать ИИ.
2. Привязать запись к существующему занятию (`appointments`).
3. Завести минимальную отдельную сущность «урок».

Хранение результата:

1. Колонки прямо в таблице урока.
2. Отдельная таблица транскрипта (один к одному с уроком), реплики - списком в JSON.
3. Отдельная таблица, где каждая реплика - своя строка.

**Решение.** Отдельный урок (`lessons`), отдельный транскрипт (`lesson_transcripts`) с репликами в `JSONB` и отдельная таблица участников (`lesson_participants`) для доступа.

**Как устроено.**

```
users ─┬──< lessons ──── lesson_transcripts      (один урок - один транскрипт)
       │      │
       │      └──< lesson_participants >──┐      (с кем автор поделился)
       └──────────────────────────────────┘
```

`lessons` - урок, данные автора:

| Колонка | Тип | Зачем |
|---|---|---|
| `id` | UUID, PK | Номер урока. UUID, а не 1, 2, 3: номер нельзя угадать перебором |
| `teacher_id` | int, FK → `users.id`, индекс, `ON DELETE CASCADE` | **Автор записи.** Им может быть и специалист, и ученик; название колонки осталось от первой версии, где загружал только специалист |
| `title` | varchar(255) | Название |
| `topic` | varchar(500), может быть пустым | Тема: подсказка для распознавания терминов |
| `transcription_model` | enum `FAST` / `QUALITY` | Какой вариант распознавания выбрал автор |
| `audio_path` | text | Путь к файлу на диске (`media/lessons/{id}.{ext}`). Наружу через API не отдаётся |
| `audio_size_bytes` | bigint, может быть пустым | Размер файла, по нему считается суточный лимит (раздел 4) |
| `created_at`, `updated_at` | timestamptz | Когда загружен; по `created_at` сортируется список и считается лимит |

`lesson_transcripts` - результат распознавания:

| Колонка | Тип | Зачем |
|---|---|---|
| `id` | UUID, PK | Номер транскрипта; именно его получает задача воркера |
| `lesson_id` | UUID, FK → `lessons.id`, **уникальный** индекс, `ON DELETE CASCADE` | Связь с уроком. Уникальность гарантирует «один урок - один транскрипт» на уровне базы |
| `status` | enum `PENDING` / `PROCESSING` / `DONE` / `FAILED` | Где сейчас распознавание |
| `language` | varchar(16) | Язык, который определила модель |
| `segments` | JSONB | Реплики: `[{"start": 679.2, "end": 684.9, "text": "...", "speaker": null}, ...]` |
| `error` | text, до 1000 символов | Текст ошибки при `FAILED` |
| `note` | text | Предупреждение при `DONE`, например «модель зациклилась, текст получен запасным вариантом» |

`lesson_participants` - с кем автор поделился уроком:

| Колонка | Тип | Зачем |
|---|---|---|
| `id` | UUID, PK | |
| `lesson_id` | UUID, FK → `lessons.id`, индекс, `ON DELETE CASCADE` | Какой урок |
| `user_id` | int, FK → `users.id`, индекс, `ON DELETE CASCADE` | Кому открыт |
| | `UNIQUE (lesson_id, user_id)` | Один человек не может быть добавлен к уроку дважды |

**Почему.**

- ИИ-части от домена нужен только идентификатор урока. Первый источник записи - загрузка готового файла, ей не нужны ни слоты, ни расписание. Привязка к `appointments` запретила бы офлайн-уроки и записи вне расписания, а перестройка домена заранее надолго оставила бы нас без результата.
- Урок - это данные человека (название, тема, файл), а транскрипт - результат работы машины со своим жизненным циклом (статус, ошибка, повтор). Их удобно менять независимо. На этапе 2 рядом появятся конспект и вопросы со своими статусами.
- Реплики всегда читаются и пишутся целиком, по одной их искать не нужно. Отдельная строка на реплику дала бы тысячи строк на урок без всякой пользы.
- **Единый формат реплик** `{start, end, text, speaker}`: любой будущий источник (загрузка, видеосвязь) и любой движок приводятся к нему, дальше работает один и тот же код.
- `FAILED` - только настоящая ошибка. Если текст есть, но с оговоркой, статус `DONE`, а оговорка в `note`.
- Важные правила заданы **в самой базе**, а не только в коде: уникальность транскрипта, уникальность участника, каскадное удаление. Даже при ошибке в коде база не даст создать второй транскрипт или оставить «висящих» участников удалённого урока.

**Цена решения.** Искать по тексту средствами базы неудобно, поиск по репликам добавим отдельно, когда понадобится. Колонка `teacher_id` называется не по смыслу (это автор любой роли); переименование отложено, чтобы не делать лишнюю миграцию.

**Где в коде.** `backend/src/models/lesson.py`, `lesson_transcript.py`, `lesson_participant.py`; миграции `b7c1d2e3f4a5_lessons_and_transcripts.py`, `f3a9c2d71b84_lesson_participants.py`, `a6d4e8b2c915_lesson_audio_size.py`.

## 2. Кто видит результат транскрибации

**Вопрос.** Запись и расшифровка урока - личные данные. Кто их видит и кто решает, кому их показать? Как сделать одно правило и для специалиста, и для ученика?

**Варианты.**

1. Только тот, кто загрузил запись (так было в первой версии страницы).
2. Привязать урок к занятию: видят все участники занятия.
3. Автор сам отмечает, с кем поделиться, выбирая из людей, с кем у него были занятия.
4. Делиться с любым пользователем по email.

**Решение.** Третий вариант, одинаковый для обеих ролей. Загрузить запись может любой вошедший пользователь. Доступ к уроку есть у двух групп людей:

- **автор** - `lessons.teacher_id` равен id пользователя;
- **участник** - есть строка в `lesson_participants` с этим `lesson_id` и `user_id`.

Больше доступа нет ни у когоI.

**Как устроено.**

**Шаг 1. Кто делает запрос.** Все маршруты `/lessons` используют зависимость `get_any_user_id`: она проверяет JWT-токен и достаёт из него `user_id`. id пользователя никогда не берётся из тела запроса или адреса, поэтому выдать себя за другого нельзя.

**Шаг 2. С кем можно поделиться (контакты).** Контакт - человек, с которым у пользователя было хотя бы одно неотменённое занятие, причём в другой роли. Для специалиста это его ученики, для ученика - его преподаватели. Запрос (`LessonParticipantDAO._contacts_query`) соединяет таблицу участников занятий саму с собой:

```sql
SELECT other.user_id,
       coalesce(client_profiles.name,
                specialist_profiles.first_name || ' ' || specialist_profiles.last_name) AS name,
       max(slot.starts_at) AS last_appointment_at
FROM appointments_attendees AS me
JOIN appointments_attendees AS other ON other.appointment_id = me.appointment_id
JOIN appointments                 ON appointments.id = me.appointment_id
JOIN specialist_availability_slots AS slot ON slot.id = appointments.slot_id
LEFT JOIN client_profiles     ON client_profiles.id = other.user_id
LEFT JOIN specialist_profiles ON specialist_profiles.id = other.user_id
WHERE me.user_id = :текущий_пользователь
  AND other.role <> me.role            -- ученики одной группы друг другу не контакты
  AND appointments.cancelled_at IS NULL
GROUP BY other.user_id, name
ORDER BY last_appointment_at DESC
```

Этот же запрос с условием `other.user_id = :кого_добавляют` и `LIMIT 1` проверяет, можно ли добавить конкретного человека (`is_contact`). Список и проверка не могут разойтись: условие написано один раз.

**Шаг 3. Поделиться** (`POST /lessons/{id}/participants`, тело `{"user_id": 42}`). Сервис `add_participant` проверяет по порядку:

1. Урок существует и пользователь его автор, иначе 404 (чужой урок) или 403 (участник пытается добавить кого-то).
2. Нельзя добавить самого себя - 422.
3. Добавляемый - контакт автора (шаг 2), иначе 403.
4. Если строка уже есть, ничего не происходит (повторный запрос безопасен), иначе вставляется строка в `lesson_participants`.

**Шаг 4. Чтение урока и текста.** Каждый запрос к конкретному уроку проходит через одну функцию `_get_visible_lesson(user_id, lesson_id)`:

```
найти урок по id
├─ нет такого урока                          → 404
├─ lessons.teacher_id == user_id             → (урок, автор)
├─ есть строка lesson_participants(урок, user) → (урок, участник)
└─ иначе                                     → 404  (тот же ответ, что «урока нет»)
```

Для действий только автора есть обёртка `_get_owned_lesson`: она вызывает ту же функцию и отвечает 403, если пользователь участник. Так правило «кто вообще видит урок» записано в одном месте, а не повторяется в каждом методе.

**Шаг 5. Что именно отдаётся.** Сервис получает из шага 4 признак «автор или участник» и по нему обрезает ответ:

| Данные | Автор | Участник | Остальные |
|---|---|---|---|
| Урок: название, тема, дата (`GET /lessons/{id}`) | да | да, с `is_owner: false` | 404 |
| Статус распознавания | все 4 статуса | `PROCESSING` и `FAILED` превращаются в `PENDING`: видно только «готово» или «ещё нет» | 404 |
| Текст с таймкодами (`GET /lessons/{id}/transcript`) | да | да, когда `DONE`; до этого - пустой список реплик | 404 |
| Текст ошибки (`error`), предупреждение (`note`), язык до готовности | да | нет, поля обнуляются | 404 |
| Повтор (`/retry`), список участников, добавление участников | да | 403 | 404 |
| Убрать участника (`DELETE .../participants/{user_id}`) | любого | только себя, иначе 403 | 404 |
| Аудиофайл | через API не отдаётся никому | | |
| Конспект, вопросы и ответы (этап 2) | да | после проверки автором | 404 |

**Шаг 6. Списки.** `GET /lessons/?scope=own` - свои уроки (`WHERE lessons.teacher_id = :я`), `scope=shared` - присланные (`JOIN lesson_participants ... WHERE lesson_participants.user_id = :я`). Статус транскрипта подтягивается тем же запросом (`LEFT JOIN lesson_transcripts`), а не отдельным запросом на каждый урок. Список постраничный: `limit` от 1 до 100 (по умолчанию 20) и `offset`.

**Шаг 7. Удаление.** Убрать участника - удалить строку из `lesson_participants`, доступ пропадает со следующим же запросом. При удалении урока или пользователя строки удаляются каскадом (`ON DELETE CASCADE`).

**Почему.**

- Привязка к занятию отсекла бы офлайн-уроки и записи вне расписания, а одну запись нельзя было бы показать людям из разных занятий. Поэтому связь с занятиями используется только для проверки «знакомы ли эти люди», а не для самого доступа.
- Добавление по email позволило бы перебором узнать, кто зарегистрирован, и прислать текст человеку без его согласия. Правило «только те, с кем было занятие» закрывает обе проблемы.
- **Чужой урок отвечает 404, а не 403**: по ответу нельзя понять, существует ли урок с таким номером.
- **Участник видит статус в упрощённом виде**: ошибки и ход распознавания - служебная информация автора, и только автор может что-то с ними сделать.
- **Сырой текст показывается участнику сразу**: это запись речи, пусть и с ошибками распознавания. Конспект же составит нейросеть, которая может «додумать» факт, а участник примет это за слова автора. Поэтому конспект и ответы сначала проверяет автор.
- Чтобы не выбрать не того человека, рядом с именем в списке контактов показывается дата последнего занятия (`last_appointment_at`), а участника можно убрать в один клик. Участник может убрать себя сам: преподавателю не обязательно хранить все присланные записи.

**Цена решения.** На групповой записи каждый участник увидит реплики всех. При загрузке нужно предупреждать, что записывать чужую речь можно только с согласия; юридическую сторону перед реальным запуском должен проверить специалист. Если занятие отменят после того, как запись открыли, доступ сохранится: контакт проверяется только в момент добавления.

**Где в коде.** `backend/src/services/lesson/lesson_service.py` (`_get_visible_lesson`, `_get_owned_lesson`, `add_participant`, `remove_participant`, `get_transcript`, `_to_schema`), `backend/src/crud/impl/lesson_participant.py` (`_contacts_query`, `is_participant`), `backend/src/crud/impl/lesson.py` (`find_by_teacher`, `find_shared_with`), `backend/src/api/lessons.py`, тесты `backend/tests/integration/api/test_lesson_participants.py`. Полное описание правил - раздел 11 [TRANSCRIPTION.md](TRANSCRIPTION.md).

## 3. Распознавание в отдельном воркере

**Вопрос.** Распознавание часовой записи на процессоре занимает минуты, а модель занимает 1,5-2 ГБ памяти. Как встроить это в веб-приложение?

**Варианты.**

1. Распознавать прямо в обработчике запроса.
2. Фоновая задача внутри процесса API (`BackgroundTasks` в FastAPI).
3. Отдельный процесс-воркер с очередью (Celery и Redis, они уже были в проекте).

**Решение.** Третий вариант. Воркер выполняет одну задачу за раз (`concurrency=1`).

**Как устроено.** Путь одной записи, с тем, что происходит в базе на каждом шаге:

```
1. POST /lessons/ (файл, название, тема, вариант)                      [процесс API]
   ├─ проверить расширение и суточный лимит (раздел 4)
   ├─ записать файл на диск кусками по 1 МБ → media/lessons/{lesson_id}.{ext}
   ├─ INSERT lessons (..., audio_path, audio_size_bytes)
   ├─ INSERT lesson_transcripts (lesson_id, status = PENDING)
   ├─ COMMIT
   └─ отправить в Redis задачу transcribe_lesson(transcript_id), ответить 201

2. Воркер берёт задачу                                                  [процесс воркера]
   ├─ транзакция 1: если статус уже PROCESSING или DONE - выйти;
   │                иначе UPDATE status = PROCESSING; COMMIT
   ├─ распознавание (минуты, без открытой транзакции)
   └─ транзакция 2: UPDATE status = DONE, segments, language, note     — успех
                    или UPDATE status = FAILED, error                  — ошибка

3. Сайт раз в 5 секунд: GET /lessons/{id} → transcript_status
   когда DONE:          GET /lessons/{id}/transcript → segments
```

Важные детали:

- **COMMIT до отправки задачи в очередь.** Иначе воркер может взять задачу раньше, чем строки появятся в базе, и не найти транскрипт.
- **В задачу передаётся только `transcript_id`**, а не файл и не параметры. Всё остальное воркер читает из базы: так задача всегда работает с актуальными данными.
- **Повторный запуск задачи безопасен.** Если Celery доставит ту же задачу дважды, вторая увидит `PROCESSING` или `DONE` и ничего не сделает.
- **`PROCESSING` фиксируется отдельной транзакцией сразу**, а распознавание идёт вне транзакции: иначе транзакция в базе держалась бы открытой минутами, а сайт не видел бы, что работа началась.
- **Файл не читается в память целиком.** Если загрузка оборвалась, нарушила лимит или запись в базу не удалась, недописанный файл удаляется с диска.
- В `error` попадает только текст ошибки (до 1000 символов), полный traceback пишется в лог воркера.

**Почему.**

- Запрос не может висеть минутами: соединение оборвётся, а пользователь не поймёт, что происходит.
- Модель в процессе API отнимала бы память и процессор у обычных запросов, а при перезапуске API задача терялась бы.
- Воркер перезапускается и масштабируется отдельно от API.
- Две задачи параллельно на одном процессоре не быстрее одной, а памяти нужно вдвое больше. Поэтому одна задача за раз.

**Цена решения.** Записи распознаются по очереди: большая загрузка одного пользователя задерживает остальных (отсюда лимит, раздел 4). API и воркер делят файлы через общую папку; для нескольких серверов понадобится общее хранилище (S3 или MinIO). Если воркер умрёт посреди работы, транскрипт навсегда останется в `PROCESSING` (раздел 7).

**Где в коде.** `backend/src/services/lesson/lesson_service.py` (`create_lesson`, `_save_audio`), `backend/src/tasks/transcribe_lesson.py`, `backend/src/services/transcription/pipeline.py` (`start_processing`, `save_result`, `save_failure`), сервис `worker` в `compose.yml`.

## 4. Лимит на загрузку записей

**Вопрос.** Воркер распознаёт по одной записи. Когда загружать начнут и ученики, один человек сможет занять очередь на часы. Как это ограничить?

**Варианты.**

1. Лимит по длительности записей (минуты в сутки).
2. Лимит по количеству загрузок.
3. Лимит по суммарному размеру файлов за последние 24 часа.

**Решение.** Третий вариант. Каждый пользователь может загрузить не больше `LESSON_DAILY_UPLOAD_MB` мегабайт за последние 24 часа (по умолчанию 1000). Окно скользящее: место освобождается через сутки после каждой загрузки, а не в полночь.

**Как устроено.**

1. Перед записью файла сервис считает, сколько пользователь уже загрузил (`LessonDAO.uploaded_since`):

   ```sql
   SELECT coalesce(sum(audio_size_bytes), 0), min(created_at)
   FROM lessons
   WHERE teacher_id = :я AND created_at >= now() - interval '24 hours'
   ```

   Индекс по `teacher_id` уже есть, поэтому запрос дешёвый.
2. Остаток = лимит − сумма. Если остатка нет, сразу ответ 429, файл даже не начинает записываться.
3. Пока файл пишется на диск кусками по 1 МБ, после каждого куска сравниваются записанные байты с остатком и с пределом на один файл (500 МБ). Как только предел превышен, запись прерывается, недописанный файл удаляется, ответ 429 (или 413 для одного слишком большого файла).
4. При успехе размер сохраняется в `lessons.audio_size_bytes` и с этого момента входит в сумму.
5. Текст ответа 429 говорит, когда лимит начнёт освобождаться: `min(created_at) + 24 часа − сейчас`, например «через 3 ч 15 мин».

**Почему.**

- Длительность до распознавания неизвестна: чтобы её узнать, файл нужно разобрать. А размер виден сразу, во время загрузки, и загрузку можно прервать, не принимая лишние сотни мегабайт.
- Количество загрузок ничего не говорит о нагрузке: десять коротких файлов легче одного часового.
- Отдельная таблица для учёта не нужна: всё считается из `lessons`, где размер и время загрузки и так хранятся.
- Уроки, загруженные до появления лимита, размера не имеют (`NULL`) и в сумму не входят, поэтому миграции не пришлось заполнять старые данные.
- Лимит задаётся в `.env`, поэтому на этапе тестирования его можно поднять без правки кода.

**Цена решения (известные ограничения).**

- Несжатый `wav` при той же длительности весит в разы больше `m4a` и быстрее расходует лимит.
- Повтор распознавания (`/retry`) в лимит не входит, поэтому один файл можно перезапускать много раз. Если это станет проблемой, нужен отдельный лимит на число повторов, а не учёт повторов в мегабайтах.
- Проверка идёт без блокировки, и две одновременные загрузки одного человека могут превысить лимит на размер одной загрузки. Для защиты очереди этого достаточно.

**Где в коде.** `backend/src/services/lesson/lesson_service.py` (`_daily_upload_left`, `_save_audio`, `DailyQuota`), `backend/src/crud/impl/lesson.py` (`uploaded_since`), `backend/src/config/settings.py`, миграция `a6d4e8b2c915_lesson_audio_size.py`, тесты `backend/tests/integration/api/test_lesson_upload_limit.py`.

## 5. Защита от зацикливания модели

**Вопрос.** Whisper иногда застревает на одной фразе и повторяет её десятки раз, теряя остаток записи. При этом ошибки нет, задача формально завершается успешно. Что делать?

**Варианты.**

1. Ничего не делать, пользователь сам заметит.
2. Обнаружить зацикливание и поставить `FAILED`.
3. Обнаружить и автоматически перераспознать запись другим вариантом, не теряя результат.

**Решение.** Третий вариант.

**Как устроено.**

1. После распознавания весь текст склеивается в один поток слов (регистр, пунктуация и «ё» не учитываются) и проверяется на повторы: фраза длиной до 8 слов, повторённая подряд 5 и более раз. Повтор через границу реплик тоже находится.
2. Если выбранный вариант «Точнее» зациклился, та же запись автоматически распознаётся вариантом «Быстро», и сохраняется его текст.
3. Результат не выбрасывается никогда. Статус всегда `DONE`, а что случилось, написано в `lesson_transcripts.note`:
   - запасной вариант справился - его текст и предупреждение, на какой фразе зациклилась модель;
   - зациклились оба варианта или сразу был выбран «Быстро» - текст с предупреждением, что конец записи мог распознаться неверно;
   - запасной вариант упал - первый текст с предупреждением.

**Почему.**

- Порог 5 подобран на реальных текстах. Лектор может повторить фразу 2-3 раза, это нормальная речь. Детектор не сработал ни на одной из 15 нормальных расшифровок и на 78-минутной лекции, но поймал оба известных зацикливания (32 и 5 повторов).
- Сохранить текст с предупреждением полезнее, чем поставить `FAILED`: часть текста почти всегда пригодна.
- Запасной проход стоит около 17 секунд на двухминутной записи, и платим мы его только при сбое.

**Цена решения.** Ловятся только повторы подряд, другие «галлюцинации» (выдуманный текст на тишине) - нет. Если слово намеренно сказано 5 раз подряд, появится лишнее предупреждение.

**Где в коде.** `backend/src/services/transcription/loops.py` (поиск повторов), `guarded.py` (запасной вариант и текст предупреждения).

## 6. Движок распознавания и как его заменить

**Вопрос.** Чем распознавать речь и как не привязаться к одному движку?

**Варианты.** Облачные сервисы (платные или с ключами), оригинальный Whisper, faster-whisper.

**Решение.** faster-whisper локально, за интерфейсом `Transcriber`; пользователь выбирает вариант, а не модель.

**Как устроено.**

```
lessons.transcription_model (FAST / QUALITY)
      ↓  catalog.py: вариант → имя модели из настроек
WHISPER_MODEL_FAST = "small",  WHISPER_MODEL_QUALITY = "large-v3-turbo"
      ↓  factory.py: создаёт объект с интерфейсом Transcriber
Transcriber.transcribe(аудио, язык, подсказка) → TranscriptionResult(language, segments)
      ↓
whisper.py: реализация на faster-whisper
```

- **`Transcriber`** - интерфейс с одним методом. Остальной код (воркер, защита от зацикливания) знает только его. Чтобы сменить движок, достаточно написать один новый класс и выбрать его в фабрике.
- **Список вариантов** отдаёт `GET /lessons/models`: id, название («Быстро», «Точнее») и описание. Имён моделей в ответе нет.
- **Подсказка для модели** - только тема урока (`lessons.topic`), которую указал автор. Название урока не передаётся: короткое название вроде `lecture3` заставляло модель писать без заглавных букв и знаков препинания (8 знаков против 43 без подсказки на одной и той же записи).

**Почему.**

- faster-whisper бесплатный, работает без ключей, записи не уходят третьим лицам. На процессоре он быстрее оригинального Whisper. Скорость и качество нескольких моделей мы замерили на настоящих лекциях.
- Если дать выбирать модель по имени, можно случайно запустить огромную модель, и слабый сервер встанет. Если модель за вариантом заменить на лучшую (например, на сервере с видеокартой), пользователям ничего менять не придётся: в базе хранится вариант, а не имя модели.

**Цена решения.** На процессоре распознавание медленное. Говорящих модель не различает: `speaker` пока всегда пустой.

**Где в коде.** `backend/src/services/transcription/` (`base.py`, `factory.py`, `catalog.py`, `whisper.py`, `pipeline.py`).

## 7. Повторный запуск распознавания

**Вопрос.** Распознавание может упасть или дать плохой результат. Как запустить его заново?

**Варианты.**

1. Автоматические повторы при сбое.
2. Ручной повтор по запросу автора, с возможностью сменить вариант («Быстро» / «Точнее»).
3. Загрузить файл заново как новый урок.

**Решение.** Второй вариант: `POST /lessons/{id}/retry`, тело по желанию `{"model": "quality"}`.

**Как устроено.** Сервис `retry_transcription` по порядку:

1. Проверяет, что пользователь - автор урока (`_get_owned_lesson`, раздел 2): участнику 403, чужому 404.
2. Если `lesson_transcripts.status = PROCESSING` - 409: запись уже распознаётся.
3. Если файла `lessons.audio_path` нет на диске - 409 с понятным текстом.
4. Если передан другой вариант - `UPDATE lessons SET transcription_model`.
5. `UPDATE lesson_transcripts SET status = PENDING, segments = NULL, language = NULL, error = NULL, note = NULL` - прежний результат стирается, строка транскрипта та же.
6. COMMIT, затем задача в очередь - как при загрузке (раздел 3).

**Почему.**

- Автоматический повтор бессмыслен при битом файле: задача падала бы снова и снова, занимая единственный воркер. Решать, повторять ли, должен человек.
- Новая загрузка того же файла тратила бы лимит и место на диске и плодила бы дубликаты уроков, а участникам пришлось бы заново открывать доступ.
- Второй параллельный запуск того же файла только впустую нагружал бы процессор.

**Цена решения.** Если воркер умер посреди работы, транскрипт остаётся в `PROCESSING` навсегда, и повтор для него запрещён. Через какое время считать задачу зависшей, пока не решено.

**Где в коде.** `backend/src/services/lesson/lesson_service.py` (`retry_transcription`).

## 8. Соединения с БД в воркере

**Вопрос.** В Docker первая задача распознавания проходила, а вторая падала через 0,06 секунды с ошибкой `attached to a different loop` и оставалась в `PENDING`.

**Причина.** Celery запускает каждую задачу через новый `asyncio.run()`, то есть в новом цикле событий. Общий пул соединений с базой из API привязывается к циклу первой задачи, и во второй задаче его соединения уже нельзя использовать.

**Решение.** Каждая задача создаёт свой движок БД без пула (`NullPool`) и закрывает его в конце (`engine.dispose()` в `finally`). Ошибка задачи теперь пишется и в лог воркера.

**Почему.** Задача длится минуты, поэтому лишнее подключение к базе на её старте ничего не стоит. Пул здесь не даёт выигрыша, а только создаёт проблему. Проверено: три задачи подряд в одном процессе воркера.

**Где в коде.** `backend/src/tasks/transcribe_lesson.py` (`_run`).

## 9. Тяжёлые зависимости только в образе воркера

**Вопрос.** faster-whisper с зависимостями весит сотни мегабайт, а модели ещё 0,5-1,6 ГБ каждая. Нужно ли это всё в образе API?

**Решение.**

- Зависимости распознавания вынесены в отдельный `requirements-transcribe.txt`. Они ставятся только в образ воркера (аргумент сборки `INSTALL_TRANSCRIBE=1`), образ API остаётся лёгким.
- Скачанные модели хранятся в отдельном томе `whisper_models` и не скачиваются заново при пересборке.
- Миграции применяет только API (`RUN_MIGRATIONS=0` у воркера), чтобы два контейнера не запускали их одновременно.

**Найденная проблема.** В Docker Desktop распознавание падало с ошибкой `cannot enable executable stack`: библиотека `ctranslate2` требует исполняемого стека, а WSL2 это запрещает. Теперь при сборке образа воркера этот флаг снимается командой `patchelf --clear-execstack`.

**Где в коде.** `backend/Dockerfile`, `backend/requirements-transcribe.txt`, `compose.yml`.

## 10. Страница записей на сайте

**Вопрос.** Как показать загрузку файла в сотни мегабайт и распознавание, которое длится минуты?

**Решение.**

- **Загрузка через `XMLHttpRequest`, а не `fetch`.** Только он показывает процент загрузки. Без процента при большом файле непонятно, идёт ли что-то вообще.
- **Статус запрашивается раз в 5 секунд** (`GET /lessons/{id}`), пока он не `DONE` или `FAILED`. Распознавание идёт минуты, мгновенное обновление не нужно. Опрос гораздо проще WebSocket и работает через тот же API.
- **Открытый урок хранится в адресе страницы** (`?lesson=id`). Страницу можно обновить или открыть по ссылке, и она продолжит следить за тем же уроком. Пока одна запись распознаётся, можно открыть другую, уже готовую.
- **Список уроков постраничный** («Показать ещё»), сервер отдаёт не больше 100 за раз.
- Текст показывается с таймкодами, есть кнопка «Скопировать». Для слишком большого файла (413) и неподходящего формата (415) сайт показывает свои понятные сообщения, для остальных ошибок, например лимита (429), - текст сервера.

**Цена решения.** Пока страница открыта, опрос шлёт лишние запросы. При нынешнем числе пользователей это незаметно.

**Где в коде.** `frontend-web/src/api/lessons.ts`, `frontend-web/src/app/components/Lessons.tsx`.
